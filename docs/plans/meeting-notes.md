# Meeting Notes

Capture a meeting's system audio, transcribe it, and turn the transcript into
structured notes stored in an in-app library.

## Goal

Yazar gains a second mode alongside dictation: start a meeting, let it run, stop
it, and get a set of notes (summary, decisions, action items) that persist and
can be reopened later.

## Decisions

**Meeting mode records system audio only. The microphone is never opened.**

Everything below follows from that one choice, so it is worth stating what it
buys:

- No mixing of two sources, and no sample-rate or clock drift between them.
- No microphone permission for meeting mode, and no new prompt for existing users.
- No device contention with `Recorder`, which owns the mic for dictation. The two
  modes are fully independent and can run at the same time.
- Screen Recording is the only new permission, and it is needed only by this
  feature.

The cost is real and should be surfaced in the UI rather than hidden: on a video
call your own voice is not played back through your speakers, so **you will not
appear in your own meeting transcript**. Notes will capture what everyone else
said. See "Dictated asides" for the mitigation.

**Notes are generated by OpenRouter only, for now.** The on-device Apple
Foundation Models path is deferred, not cancelled; see "Notes" for what returns
with it.

This has a privacy consequence worth stating plainly rather than burying: with no
on-device option, generating notes always sends the full meeting transcript off
the machine, and that transcript is of other people who were not asked. Apple
Speech transcription paired with OpenRouter notes is now the most private
combination available, and it still means the text leaves. The settings copy
should say so in the same direct way `TranscriptionProvider.summary` already
does for audio.

**Transcripts are merged and unattributed.** No diarization, no speaker labels.

## What this deliberately does not do

- Does not record the microphone during a meeting.
- Does not attribute lines to speakers.
- Does not join, schedule, or integrate with any meeting platform.
- Does not change dictation behaviour in any way.
- Does not generate notes on device.

## Architecture

### Capture

New `SystemAudioRecorder`, parallel to `Recorder` rather than an extension of it.
`Recorder` is tuned for the opposite problem: a reused `AVCaptureSession` with a
~100 ms warm start and an in-memory drain, sized for a few seconds of hold-to-talk.
Meeting capture is long-form and streaming, so it gets its own type.

Uses `SCStream` from ScreenCaptureKit:

- `SCStreamConfiguration.capturesAudio = true`, `sampleRate = 16_000`,
  `channelCount = 1` to land directly in Yazar's canonical format.
- `excludesCurrentProcessAudio = true`. Without this, Yazar's own status sounds
  are recorded into the meeting.
- `captureMicrophone` stays **false**. This is the decision above, expressed in
  one line of config.
- An `SCContentFilter` is required even for audio-only capture. Build one from
  `SCShareableContent`, then add only the `.audio` stream output and no `.screen`
  output, so no video frames are ever produced.
- Sample delivery arrives on a dispatch queue, the same shape as
  `Recorder.captureOutput`. Reuse `CaptureSink`'s conversion logic for the format
  conversion; do not reuse its unbounded accumulation.

Note for the UI: capturing system audio lights the macOS screen-recording
indicator for the duration of the meeting. Say so on the start control rather
than letting the user discover it.

### Meeting detection

Detect that a meeting is happening and **offer** to record it. Never start a
recording on a heuristic. A false positive that merely shows a prompt is a minor
annoyance; a false positive that silently records other people is not something
to hand a user by default.

**The signal is microphone occupancy, not app lifetime.** Watching
`NSWorkspace` for Teams launching is the obvious approach and the wrong one:
Teams runs all day, so the prompt would arrive at login rather than at meeting
time. `kAudioDevicePropertyDeviceIsRunningSomewhere` on the default input device
reports whether any process currently holds the microphone. Teams, Zoom, and
Meet open it when a call starts and release it when the call ends, so it tracks
the meeting itself. It needs no new permission, and `AudioInput` already does
Core Audio work of this kind.

Use `AudioObjectAddPropertyListenerBlock` rather than polling, and narrow the
result with a bundle identifier check against `NSWorkspace.runningApplications`.

Known limits, none of them fatal but all worth stating in the UI rather than
pretending to certainty:

- **Yazar trips its own detector.** `Recorder` opens the microphone for every
  dictation. Self-exclusion is mandatory, not an optimisation.
- **A browser is ambiguous.** Meet in a tab is indistinguishable from any other
  page using the microphone.
- **The signal and the capture do not match.** Microphone occupancy is the
  trigger, but meeting mode records system audio. A call where nobody ever opens
  a microphone would go undetected, and unrelated microphone use looks like a
  meeting.
- **Mute behaviour is app-dependent.** Most clients keep the device open while
  muted, but that is a convention rather than a guarantee.

Because the prompt can fire on unrelated microphone use, it needs a setting to
turn off. Default it on: the prompt is the feature.

### Storage of in-flight audio

`CaptureSink` accumulates into a single `Data` and drains at the end. At 16 kHz
mono 16-bit that is 32 KB/s, so an hour is ~115 MB held in memory with no crash
safety.

Instead, append canonical PCM incrementally to a working file as it arrives.
After transcription succeeds, discard the audio by default and keep only the
transcript and notes; an optional setting can convert it to m4a and keep it.
Retaining raw WAV per meeting is not a sensible default at ~115 MB/hour.

This is a policy change. `README.md` currently states that Yazar does not write
recordings to disk. That claim must be scoped to dictation, which remains true.

### Transcription

**Apple Speech** is in better shape than expected. `AppleSpeechTranscriber`
already drives `SpeechAnalyzer` through an `AsyncStream<AnalyzerInput>`; it
simply yields one buffer and finishes. Keeping the stream open and yielding
buffers as they arrive is a small change and produces a live transcript during
the meeting for almost nothing. Refactor so the existing one-shot dictation path
becomes a thin wrapper over a streaming core, rather than duplicating the
analyzer setup.

**OpenRouter** cannot be used as-is. `OpenRouterTranscriber` base64-encodes the
whole WAV into a JSON body under a 30 s request timeout and a 35 s task timeout;
an hour of audio becomes a ~153 MB body. For meetings it needs:

- Chunking into 30-60 s segments, split on silence rather than on a fixed clock.
  A silence detector can be built from the RMS logic already in
  `Recording.containsSpeech`.
- A per-chunk timeout instead of one timeout for the whole recording.
- Sequential upload with concatenation of results.
- Awareness that chunk boundaries lose cross-chunk context, and that an hour of
  transcription has a real per-meeting cost. Both are worth showing the user.

### Notes

One provider, one path:

    protocol NoteMaker { func makeNotes(from: Transcript) async throws -> Notes }

`OpenRouterNoteMaker` calls `/chat/completions`, which is new; only
`/audio/transcriptions` is used today. It reuses the Keychain credential but
needs its own model setting, since `openRouterModel` is the transcription model.
An hour of speech is roughly 12k tokens and fits in one prompt for any current
model, so the whole transcript goes in a single call with the gap markers intact.

**Do not add a `NotesProvider` enum yet.** Mirroring `TranscriptionProvider`
would be cargo culting the shape: that enum earns its place because it has two
real cases that differ in credentials, language handling, and privacy. A
one-case mirror is noise, and adding the enum when a second provider actually
arrives is a small change. Keep `NoteMaker` and `Notes` as the seam, which is
enough for a second implementation to slot in later.

Keep the provider-agnostic language-model client underneath `NoteMaker`
regardless. It is not speculative: roadmap item 1 needs it, and it is what makes
the deferred on-device path an addition rather than a rewrite.

**Deferred with the on-device path.** Apple Foundation Models has a ~4k token
context, so an hour of speech does not fit and that path requires map-reduce:
summarize chunks, then summarize the summaries. Two things come back with it,
recorded here so the reasoning is not rediscovered:

- Transcript chunking, which the single-prompt OpenRouter path does not need at
  all.
- A chunk boundary rule, because map-reduce destroys information the single
  prompt keeps. A chunk holding the end of a 10:00 discussion and the start of a
  14:30 one gets summarized as one continuous narrative, and the reduce step
  then sees only summaries, not the original text or the gap marker, so the
  invented continuity becomes untraceable. The rule is to prefer segment
  boundaries as chunk boundaries, subdivide only within an oversized segment,
  keep gap markers inline when a chunk holds several short segments, and never
  begin a chunk mid-segment without a "continued from earlier" note.

None of this applies while OpenRouter is the only provider.

**Interaction with the roadmap.** `docs/roadmap.md` item 1, LLM post-processing
of dictations, is the same layer. Put a provider-agnostic language-model client
underneath `NoteMaker` so "make meeting notes" and "clean up this dictation" are
two callers of one thing. Building `NoteMaker` as meetings-only guarantees a
rewrite when item 1 is picked up.

### UI

The existing app window is a settings surface with a fixed size range
(`YazarView.minimumSize` / `maximumSize`) and a page enum. A meetings library is
a list-detail browser and does not belong there. Add a separate window, built the
same way `AppDelegate.showApp()` builds the current one, holding a
`NavigationSplitView` over the meeting list.

Menu bar gains a start/stop meeting item and a recording state. `menuBarIcon`
currently switches on `yazar.state`; it will need to account for a meeting being
active independently of dictation state.

### Sleep and interruption

A meeting is long and mostly passive, so idle sleep is the default outcome
rather than an edge case: an hour of listening without touching the keyboard is
precisely what triggers it. Hold a power assertion for the duration of the
session.

    let token = ProcessInfo.processInfo.beginActivity(
        options: .userInitiated,
        reason: "Recording a meeting"
    )

`.userInitiated` already implies `idleSystemSleepDisabled` along with sudden and
automatic termination disabled. Do **not** add `.idleDisplaySleepDisabled`:
capture is unaffected by the display sleeping, and keeping the screen lit for an
hour is a battery cost with no benefit.

Tie the token's lifetime to the session the way `Yazar` ties Escape capture to
its state, so that every path which ends or abandons a meeting also calls
`endActivity`, including the failure paths. A leaked assertion is user-visible in
`pmset -g assertions` and keeps the machine awake indefinitely. A crash needs no
cleanup: the kernel releases assertions when the process dies.

This does not make the interruption path unnecessary, because it only prevents
*idle* sleep. Lid close, Apple menu > Sleep, the power button, and critical
battery all still sleep the machine, and on Apple Silicon laptops a lid close
sleeps regardless of any assertion. So:

- Observe `NSWorkspace.willSleepNotification`. It grants a short window before
  sleep; use it to stop the stream cleanly, flush the audio file, and mark the
  meeting as ended by sleep rather than leaving it in a recording state.
- Observe `NSWorkspace.didWakeNotification` to surface what happened.

The assertion narrows this from the common case to a deliberate user action,
which is what makes "end the meeting on sleep" an acceptable answer rather than a
frequent, surprising data loss.

### Resuming, quitting, and recovery

A stopped meeting can be resumed, and a meeting interrupted by the app quitting
is preserved as a snapshot. These are the same mechanism: an involuntary quit is
a pause the user did not choose, and recovery is the resume path with a different
trigger.

**A meeting is a sequence of segments, not one recording.** `SCStream` cannot be
resumed, so each run creates a new one. Model `Meeting` as an ordered list of
segments, each with a wall-clock start and end.

Two properties of the capture format make this cheap, and are the reason to keep
storing raw canonical PCM during capture rather than WAV or m4a:

- Appending across resumes is a plain file append. There is no container header
  to rewrite, so segment N+1 simply continues the same file.
- Truncation is harmless. A file cut off mid-write by a crash is just a shorter
  recording, not a corrupt one.

`Recording.wavData` already builds the header on demand, so the WAV framing stays
a transcription- and export-time concern.

Record segment boundaries even though the audio is contiguous. The gap between
stopping and resuming is real time that did not get recorded, and the detail view
should be able to show it rather than presenting two hours apart as continuous
speech.

**Transcription follows the segments.** Each resume starts a new
`SpeechAnalyzer` session, so transcribe per segment and append to the meeting's
transcript. This falls out naturally from the streaming live-transcript design
and needs no separate batch path.

**Mark user-initiated gaps in the transcript.** When a segment was ended by the
user and the next one begins more than a couple of minutes later, insert a
marker such as `[resumed after 4h]` at the seam before the transcript reaches
`NoteMaker`. Without it the model reads a deliberate four-hour break as
continuous speech and invents causal links across it. Short gaps need no marker;
a twenty-second pause is noise.

This requires `MeetingSegment` to record *why* it ended, not just when:
stopped by the user, or interrupted. The marker is derived at transcript-assembly
time from that reason plus the wall-clock gap, so nothing needs to be decided
during capture.

Segments that ended by interruption get a marker too, but a different one. They
are not a pause: if Yazar died at 10:25 and recovered at 10:31, the meeting kept
going and six minutes were spoken and never captured. The transcript has a hole,
and without a marker the model smooths over it and the notes read as complete.

Word it as loss rather than as a break, for example
`[recording interrupted, up to 6 minutes not captured]`. "Up to" is the honest
framing: the gap is the distance between the last captured sample and the resume,
which is an upper bound on what was missed, since the meeting may not have been
running for all of it.

So both segment-end reasons produce a marker, and the reason chooses the wording:
a user stop reads as a pause, an interruption reads as missing audio.

**Resuming invalidates notes.** If notes were already generated, resuming marks
them stale and they are regenerated from the full transcript on the next stop.
Do not attempt to incrementally extend existing notes.

**Recovery has a graceful path and an ungraceful one.**

Graceful, on `applicationWillTerminate`, which `AppDelegate` already implements
for `yazar.stop()`: finalize the segment, flush the file, and write the meeting
record as interrupted. The power assertion from the previous section helps here,
because `.userInitiated` includes `suddenTerminationDisabled`, so macOS will not
kill the process without running terminate handlers while a meeting is active.
That is a real benefit of that option beyond sleep, and worth not losing.

Ungraceful, for force quit, crash, and power loss, where no handler runs: write
the meeting metadata record at meeting start and update it at every segment
boundary and periodic flush. On launch, `MeetingStore` scans for records still
marked recording, which by definition are orphaned, and presents them in the
library as unfinished. The user can resume them or finalize them, meaning
transcribe what exists and generate notes.

`MeetingState` therefore needs to distinguish at least: recording, paused,
interrupted, transcribing, and complete. Paused and interrupted differ only in
how they were reached, and share a resume path.

### Single instance

Only one Yazar may run at a time. On launch, check for another running instance
with the same bundle identifier via
`NSRunningApplication.runningApplications(withBundleIdentifier:)`; if one exists,
activate it and terminate immediately rather than starting a second copy.

This is what makes crash recovery sound. With single-instance enforced, a meeting
record still marked recording at launch is orphaned by definition, because no
other process could be holding it. Without it, that conclusion is a guess. Doing
this removes the need for per-meeting `flock` files entirely, so it is a
simplification rather than an addition.

It also fixes a defect that already exists in the shipping app, independent of
meetings: two instances both install a hot key tap and contend for the dictation
trigger.

**Development note.** The debug build and the `/Applications` build share the
bundle identifier `egeis.yazar`, so with this in place, pressing Run in Xcode
while a release copy is running will make the debug build exit on launch. That is
correct behaviour but mystifying in silence, so log the reason on the way out.
The workflow is to quit the menu bar copy before running from Xcode.

### Permissions

Add Screen Recording to `Permissions` using `CGPreflightScreenCaptureAccess()`
and `CGRequestScreenCaptureAccess()`, following the existing
`requestMicrophone()` pattern including the fall-through to
`openPrivacySettings`.

**Do not add it to `allGranted`.** That property gates `isReadyToStart` in
`AppDelegate`, so including an optional permission there would block dictation
from starting for every user who never records a meeting. Screen Recording should
be requested on first meeting start, not during onboarding.

No entitlement changes. The app is not sandboxed; `yazar.entitlements` only
carries `com.apple.security.device.audio-input`.

## File plan

Following `AGENTS.md`: one primary type per file, files named after their type,
folders by feature.

New, `yazar/Meetings/`:

- `MeetingSession.swift` - coordinator and state machine, the meeting-mode peer
  of `Yazar.swift`
- `MeetingState.swift`
- `SystemAudioRecorder.swift` - the `SCStream` capture engine
- `MeetingAudioFile.swift` - rolling canonical-PCM writer
- `Meeting.swift` - the stored model
- `MeetingSegment.swift` - one capture run, with wall-clock bounds
- `MeetingStore.swift` - persistence and enumeration
- `MeetingDetector.swift` - microphone-occupancy watcher behind the record offer
- `MeetingsWindowController.swift`
- `MeetingListView.swift`
- `MeetingDetailView.swift`

New, `yazar/Notes/`:

- `NoteMaker.swift` - protocol
- `Notes.swift` - the structured output type
- `OpenRouterNoteMaker.swift`
- `LanguageModelClient.swift` - provider-agnostic, shared with roadmap item 1
- `AudioChunker.swift` - splits captured PCM on silence for OpenRouter
  transcription. Note this is audio, not text: transcript chunking arrives only
  with the deferred on-device path.

Modified:

- `Transcription/AppleSpeechTranscriber.swift` - extract a streaming core
- `Transcription/OpenRouterTranscriber.swift` - chunking, per-chunk timeout
- `Transcription/Transcriber.swift` - a streaming entry point alongside the
  one-shot one
- `Settings/Settings.swift` - notes model, audio retention, detection prompt
- `Settings/Permissions.swift` - screen recording, kept out of `allGranted`
- `Settings/YazarView.swift` - settings for the above
- `yazarApp.swift` - meeting menu items, meetings window, icon state,
  single-instance check on launch
- `README.md` - scope the "does not write recordings to disk" claim to dictation
- `docs/roadmap.md` - note that item 1 shares this feature's LLM layer

Storage layout: one directory per meeting under Application Support, containing
the metadata record, the transcript, the notes, and optionally the audio. Flat
files plus a `Codable` index rather than SwiftData for the first version:
inspectable, exportable, and no migration story to own. The metadata record is
also the crash-recovery marker described above, so it is written at meeting start
rather than at meeting end.

## Phases

Ordered so each phase ships something and the permission-gated work comes late.

1. **Notes from existing text.** `LanguageModelClient`, `NoteMaker`, `Notes`,
   `OpenRouterNoteMaker`, and the prompt. Fed by paste or file drop. No capture
   work, no chunking, no new permissions, and it lands the LLM layer roadmap
   item 1 needs.
2. **Storage and window.** `MeetingStore`, meetings window, list and detail,
   driven by phase 1 output. Segment model and the orphaned-meeting scan on
   launch belong here, so phase 3 has somewhere safe to write from the start.
3. **Capture.** `SystemAudioRecorder`, `MeetingAudioFile`, Screen Recording
   permission, start/stop from the menu bar.
4. **Long-form transcription.** Streaming Apple Speech with live transcript in the
   window; chunked OpenRouter.
5. **Meeting detection.** `MeetingDetector` on the input device's
   `IsRunningSomewhere` property, narrowed by bundle identifier, with
   self-exclusion for Yazar's own dictation. Surfaces an offer to start
   recording, never a recording. Setting to disable the prompt.
6. **Polish.** Silence-based chunk boundaries, audio retention setting, export,
   cost display for the OpenRouter paths.

## Dictated asides

Because meeting mode leaves the microphone free, the dictation trigger still
works while a meeting is recording. That turns the main limitation of the
system-audio-only decision into a feature: hold the dictation key during a
meeting to speak a private note, and append it to the active meeting's transcript
instead of pasting it into the focused app.

Worth building, but only after phase 4. It is the natural answer to "my own voice
is missing", and it requires no new capture work.

## Risks and open questions

- **`SCStream` audio-only reliability.** Audio-only capture with no `.screen`
  output is a less-travelled configuration. Validate early in phase 3 that
  buffers arrive steadily for a long session before building on it.
- **Long-session stability.** `SpeechAnalyzer` over a 60-minute stream is
  untested here. Memory growth and result-accumulation behaviour need a real
  soak test, not a two-minute check.
- **Consent.** Recording meetings is a two-party-consent matter in some
  jurisdictions. An explicit start action and a visible recording state are the
  right defaults; the macOS screen-recording indicator provides the second one.
